# Android 홈 광고 후속 수정

35번 실기기 검증에서 홈 세 지면 중 팀 채널 뒤만 실제 광고를 표시했다. 이 결과를 해결 완료로 처리하지 않고 다음 수정을 진행했다. 공개 배포와 iOS TestFlight 제출은 보류 상태다.

## 확인한 문제와 변경

- 기존 배너의 AdMob 자동 새로고침은 `Google 최적화`로 켜져 있었다. 앱의 실패 재시도 타이머도 별도로 `load()`를 호출해 SDK 갱신과 겹쳤다. Google의 Android 배너 문서는 자동 새로고침이 설정되어 있으면 실패 시 앱이 다시 요청할 필요가 없다고 명시한다. 앱의 타이머와 수동 `load()` 호출을 제거했다. https://developers.google.com/admob/android/banner#refresh_an_ad
- 화면 밖 지면의 최초 로딩 지연, 같은 화면을 스크롤할 때의 광고 보존, 화면 이탈과 앱 배경 전환 시 네이티브 광고 해제를 유지했다. 실패 이후 갱신도 SDK가 맡는다.
- 홈 세 지면에 전용 광고단위를 생성하고 각각 연결했다. 이는 지면별 설정과 보고를 분리하는 변경이며, 같은 ID 사용이 `No fill`의 유일한 원인이라는 증거는 없다. 새 단위 생성만으로 광고 공급이 보장된다고 주장하지 않는다.
- 새 단위는 텍스트, 이미지, 리치 미디어와 동영상을 모두 허용한다. 자동 새로고침은 Google 최적화, 최소 eCPM은 Google 최적화의 모든 가격이다. 기존 광고단위 설정과 동의 처리, 비개인화 요청은 변경하지 않았다.

## 수정본 검사

- 성능 회귀 검사 13개 통과. 실패와 SDK 갱신 실패 뒤에 앱의 추가 요청 타이머가 없고, 이미 표시한 광고와 높이가 보존되는 것을 검사했다. 세 홈 광고단위가 서로 다르며 다른 화면은 기존 단위를 유지하는 계약도 검사했다.
- 검증 전용 1.0.2(36) 로컬 릴리스 빌드 성공. 기존 업로드 인증서와 일치하며 패키지는 `com.minion.app`이다. AAB의 실제 Hermes 번들에서 새 광고단위 세 개와 진단 표시를 확인했고 JS 수동 재시도 계측 문자열은 없다.
- AAB SHA-256: `3ceb87abe23c262d60353e55e1e4e6f8fe53fae475638bf2a9ffc35e0b0482aa`.
- 진단 파일은 `.tmp/ads-placement-fix/verify-36.aab`이다. 공개 배포용 산출물이 아니다.

## 실기기 결과

Google Play의 트랙 미지정 검증 파일 36을 저장하고, 공식 개발자 검증용 APK 5개를 받았다. 모두 기존 Play 인증서와 일치함을 확인한 후 Samsung SM-S906N에 데이터 삭제 없이 업데이트했다. ADB 설치 및 개발자 APK 환경으로 실제 Play 다운로드 환경과 완전히 같지는 않다. 테스트 광고 및 테스트 기기 설정은 사용하지 않았다.

첫 실행 PID 7268에서 세 지면의 실제 광고 표시와 impression을 확인했다.

하단 광고는 뒤이은 SDK 갱신이 no-fill이어도 기존 소재가 유지됐다. 위로 스크롤했다가 아래로 돌아온 13:02 캡처에서도 같은 실제 광고를 확인했다. 세 지면이 표시될 수 있다는 검증은 통과했지만, 처음부터 세 지면이 즉시 표시된 것은 아니다.

두 번째 새 실행 PID 8919에서는 13:03:29~13:09:44 동안 중간 및 하단의 실제 광고를 다시 확인했다. 상단은 그 관측 구간 내 로드 0회로 no-fill이 반복됐다. 따라서 **재실행마다 세 지면이 안정적으로 채워지는 검증은 미통과**다. 첫 실행의 성공만으로 해결 완료나 공개 배포 가능으로 판정하지 않는다.

모든 실패 상세는 code 3, domain `com.google.android.gms.ads`, message `No fill.`, 광고 소스 응답 0개였다. 각 지면의 새 단위 ID로 요청되는 것을 네이티브 로그에서 확인했다. 앱의 수동 load와 재시도 타이머는 없다. 공급 실패의 서버 내부 원인은 이 응답으로 확정할 수 없다.

## AdMob 공급 설정 추가 확인

- 앱의 일반 카테고리 차단은 0개다. 전체 광고 유형과 모든 가격 설정이 켜져 있으며, 기존에 확인한 앱 준비 상태, 정책 센터와 app-ads.txt에도 명시적인 게재 차단은 없었다.
- [Google 최소 eCPM 문서](https://support.google.com/admob/answer/3418058?hl=en)는 신규 단위에서 최솟값 정확도가 안정화되기까지 시간이 걸릴 수 있다고 안내한다. 이를 근거로 약 13:07:45에 신규 상단 단위만 최소 eCPM을 사용중지로 바꾸고 같은 프로세스의 자동 갱신을 관측했다.
- 13:08:31과 13:09:32에도 상단 no-fill이었다. 설정 전파 및 짧은 관측 시간 때문에 단가 영향이 없다고 단정하지 않지만 개선은 확인하지 못했다. 검증 후 상단을 원래 `Google 최적화 / 모든 가격`으로 복구했다. 기존 스토어 앱의 단위 설정은 변경하지 않았다.

## 종료 상태

- 공개 출시, 심사 제출과 TestFlight 배포는 하지 않았다. Google Play 프로덕션은 34를 유지한다. 35와 36은 트랙 미지정 진단 번들이므로 배포하지 않는다. 다음 정식 빌드는 최소 37이 필요하다. 제품 버전 설정과 EAS 원격 버전은 별도로 올리지 않았다.
- 폰에는 데이터가 보존된 진단 36이 남아 있다. 앱을 종료해 추가 QA 광고 요청을 중지했다. USB 화면 유지 설정은 원래 값 0으로 복구했다.
- 세 지면 표시 가능 및 표시 후 보존은 확인했다. 반복 실행 시 초기 공급 안정성은 남은 과제다. 계정 및 광고 공급 서버의 추가 확인이 필요하며, 코드에서 no-fill을 성공으로 바꾸거나 테스트 광고를 운영 광고로 대체하지 않는다.

## 요청 옵션과 동의 후속 점검, 진단 37

이 절의 기기와 배포 상태가 위 36 검증 종료 상태보다 최신이다.

- `requestNonPersonalizedAdsOnly: true`는 설치된 라이브러리 15.8.3에서 AdMob extras의 `npa=1`로 정상 변환된다. 진단용 네이티브 로그에서도 실제 값을 확인했다. 잘못된 요청 키나 GAM의 `customTargeting` 문제는 발견하지 못했다. 공개 개인정보처리방침이 Android 비개인화 요청을 명시하므로 해당 옵션은 유지했다.
- 최초 UMP 확인이 실패하거나 광고 요청이 불가능한 상태로 끝나면 초기화 Promise가 영구 보관되던 경로를 수정했다. 진행 중 호출만 공유하며, 일시 오류는 60초 후 활성 지면에서 재확인한다. 오류가 나도 이전 세션 동의로 요청 가능한지는 UMP에서 다시 확인한다. 성공한 비허용 결과로 동의창을 자동 반복하지 않는다.
- 개인정보 옵션 창은 중복으로 열리지 않으며 창이 열리는 동안 새 광고를 차단하고, 닫힌 뒤 실제 요청 가능 상태를 다시 읽는다. 동의 읽기 실패는 요청 차단 상태를 유지한다.
- 같은 지면의 빠른 화면 재진입 요청에 60초 간격을 적용했다. SDK 갱신 성공과 실패도 간격 기준을 갱신한다. 장착된 배너에 JS `load()`나 실패 재요청 타이머를 추가하지 않았다. 화면을 나간 뒤 곧바로 재진입하면 남은 대기 시간 동안 기존 안내 공간이 보일 수 있다.
- 릴리스 난독화에서 UMP 클래스가 보존되도록 ProGuard 규칙을 추가했고, 기존 Expo 플러그인에 넣어 네이티브 프로젝트 재생성 시에도 유지되게 했다.
- 동의 오류 복구, 동시 초기화, 개인정보 옵션 중복 호출과 철회, 지면 요청 간격, 타이머 취소, ProGuard 재생성의 행동 회귀 검사와 기존 광고 성능 검사 총 24개 통과. 앱 typecheck 통과. 앱 lint 오류 0, 기존 경고 2건.

### 실제 기기와 운영 계정 근거

- Samsung SM-S906N에서 UMP는 `status=NOT_REQUIRED`, `canRequestAds=true`, `privacyOptions=NOT_REQUIRED`를 반환했다. 현재 기기의 운영 no-fill이 동의 차단 때문이라는 증거는 없다. 이 결과로 EEA 동의창의 모든 선택지를 실기기 검증했다고 주장하지 않는다.
- Google Ad Inspector의 Privacy 탭에서도 `IABTCF_gdprApplies=false`를 확인했다. 이 확인은 별도 테스트 기기 모드에서 수행했고 운영 광고 성공 횟수에 포함하지 않았다. 동의 초기화나 사용자 선택 재설정은 하지 않았다.
- AdMob 개인정보 보호 화면에서 유럽 메시지 1개 활성은 확인했다. 세부 관리 화면은 로딩에서 멈추고 직접 연결은 403을 반환하여 메시지의 세부 설정까지 재확인하지 못했다. 설정을 임의 변경하지 않았다.
- AdMob의 오늘 현재까지 보고서에서 134요청, 50일치, 26노출, 일치율 37.31%였다. 전부 비개인화 광고로 분류됐다. 기존 단위는 99요청 중 39일치, 홈 상단은 25요청 중 1일치, 중간은 6요청 중 6일치, 하단은 4요청 중 4일치다. 지연 집계 및 작은 표본으로 통제 실험 결과가 아니다. 원자료는 `artifacts/ads-consent-fix-2026-10-31/admob-report.json`이다.
- 15:21~15:36 테스트 기기 모드에서는 실제 운영 광고단위 ID를 그대로 사용해 전체 21지면의 load와 impression을 모두 확인했다. 실패 0건이다. 홈, 일정, 이적시장, 팬톡 목록과 게시글, 선수 목록과 상세, 챔피언 목록과 상세, 대회, 팬 홈과 캘린더, 매치 상세를 포함한다. `test-all-placements.log`에 누적 근거가 있다.
- 15:36 새 프로세스에서 테스트 기기 설정을 끄고 네이티브 `test=false`, `npa=1`을 확인했다. 홈 3곳, 팬톡 목록 2곳, 선수 상세 2곳의 최초 운영 광고 요청은 모두 성공했고 각각 impression도 발생했다. 홈 첫 로드는 약 1.0초, 중간 약 0.7초였다. 운영 캡처와 로그는 `live-*` 파일이다. 이후 SDK 자동 갱신에서 no-fill 2건이 발생했으므로 no-fill 자체가 제거됐다고 판정하지 않는다.
- 15:42 두 번째 새 운영 실행에서도 상단과 중간은 각각 약 0.9초와 0.6초에 표시됐다. 하단은 최초 no-fill 후 SDK 자동 갱신으로 약 61.3초 만에 로드됐다. 세 지면 모두 impression은 발생했지만 매 실행의 즉시 공급은 여전히 미통과다. 이 실행의 no-fill은 최초 실패 1건과 후속 갱신 실패 3건이었다. 하단은 갱신 실패 뒤에도 실제 소재가 남은 것을 `live-repeat-recovery.png`에서 확인했다. 기기 상태와 전체 집계는 `artifacts/ads-consent-fix-2026-10-31/result.json`에 기록했다.

### 진단 파일과 기기 유지 상태

- 동일 업로드 키의 릴리스 진단 1.0.2(37)을 빌드했다. SHA-256은 `e65b355688486ae64822b277e9a68686b6722339120cdb1d2ac9d4e8e796ce19`다. 테스트 모드와 Inspector 진입은 임시 Metro 변환에만 있으며 제품 소스에는 없다.
- 기존 사용자 승인 범위인 검증 파일 업로드와 미출시 저장만 실행했다. Play 인증서가 일치하는 개발자 APK 5개를 받아 데이터 삭제 없이 설치했다. 최종 API 검사에서 프로덕션 34, alpha 26, internal 8과 beta 초안이 그대로임을 확인했다. 심사, 공개 배포와 테스트 사용자 배포는 하지 않았다.
- 37도 공개 배포 금지 진단 파일이다. 정상 릴리스 출력 위치의 진단 AAB는 보관본과 해시 일치를 확인한 뒤 제거했다. `.tmp/ads-consent-fix/verify-37.aab`에만 보관하며 다음 정식 Android 빌드는 최소 38을 사용해야 한다. 정식 빌드에는 진단용 Metro 변환과 네이티브 오버라이드를 사용하지 않는다.
- 사용자가 2026-10-31에 배포 지시 전까지 유지하라고 명시했으므로 USB 화면 유지 값 2를 남긴다. 원래 값은 0이며 `artifacts/ads-consent-fix-2026-10-31/device-settings.json`에 기록했다. 다음 배포 요청을 수행할 때 0으로 복구한다.
- 검증 뒤 앱은 배경으로 보내 추가 QA 광고 요청을 중단했다. 진단 37과 앱 데이터는 폰에 유지했으며 USB 화면 유지 값 2도 다시 확인했다.
