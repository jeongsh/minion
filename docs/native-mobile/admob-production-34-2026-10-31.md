# Android 34 실제 광고 미표시 조사

2026-10-31 사용자가 Google Play에서 받은 1.0.2(34)에서 캘린더 아래 광고만 표시되고 홈의 나머지 두 지면에는 `광고영역`이 남는다고 보고했다. 배포 요청은 사용자가 잠시 중단한 상태이며, 이번 조사는 배포를 재개하지 않는다.

## 기기에서 확인한 결과

USB로 연결된 Samsung SM-S906N의 운영 패키지 `com.minion.app`이 versionCode 34, versionName 1.0.2임을 확인했다. 앱을 재설치하거나 계정 및 광고 설정을 변경하지 않고 해당 프로세스의 광고 로그만 읽었다.

| 한국 시각 | 지면 | 결과 |
| --- | --- | --- |
| 11:52:09 | home-insights | error-code-no-fill, retries 0 |
| 11:52:09 | home-top | error-code-no-fill, retries 0 |
| 11:52:11 | home-teams | error-code-no-fill, retries 0 |
| 11:53:13 | home-insights | error-code-no-fill, retries 1 |
| 11:53:13 | home-teams | error-code-no-fill, retries 1 |
| 11:53:14 | home-top | loaded, 약 320x100dp |
| 11:53:15 | home-top | impression |

세 지면의 광고 요청은 실제로 시작됐다. 이 사례의 하단 두 지면 미표시에는 Google의 no-fill 응답이라는 직접적인 근거가 있다. 상단 지면도 첫 요청은 실패했지만 재시도에서 소재를 받았고 실제 노출 콜백까지 발생했다. 저장한 로그 범위 밖의 후속 공급 결과는 판정하지 않는다.

Google의 오류 코드 안내에서 no-fill은 요청은 성공했지만 당시 적합한 광고가 반환되지 않은 상태다. 테스트용 데모 단위의 광고 공급 성공은 운영 단위의 공급을 검증한 결과가 아니다.

- https://support.google.com/admob/answer/15090849?hl=ko
- https://support.google.com/admob/answer/9388275?hl=ko

## AdMob 읽기 전용 확인

기존 로그인된 MINION 계정의 관리 화면에서 다음을 확인했다. 설정은 저장하거나 변경하지 않았다.

- 앱 패키지: com.minion.app
- 앱 승인 상태: 준비됨
- 상태 세부정보: 광고 게재 사용 설정됨
- 운영 배너: MINION_Android_Banner, ca-app-pub-7060554754100656/3660217360. 앱 코드의 ID와 일치한다.
- 배너의 게재빈도 제한: 적용 불가
- 최소 eCPM: Google 최적화, 모든 가격 선택. 높은 수동 최솟값이 설정된 상태가 아니다.
- 정책 센터: 현재 정책 위반 문제 없음. 앱의 광고 게재를 중지하거나 제한하는 문제가 없다고 표시됐다.

이 확인으로 해당 화면에 표시된 승인 보류, 정책 제한과 높은 최솟값 문제는 발견되지 않았다. 개별 no-fill 응답에 대한 더 세부적인 광고 수요 및 입찰 원인은 현재 SDK가 전달하는 오류 코드만으로 확정할 수 없다. 특정 사용자나 모든 지면에서 광고가 항상 채워진다고 보장하지 않는다.

## 34와 성능 진단 앱의 구분

- 스토어 AAB 34의 로컬 산출물 시각은 10:01이며 공용 배너는 당시 LARGE_BANNER 방식이다.
- 이후 성능 작업에서는 화면 접근 시 로드와 화면 이탈 및 배경 전환 시 해제를 추가했다. 병행 작업의 anchored adaptive 변경도 보존했다.
- 마지막 성능 진단 APK는 11:23에 생성한 별도 패키지 `com.minion.app.perf`이고 Google 데모 광고 단위를 사용했다. 세 지면의 테스트 광고 로드는 확인했지만 실제 운영 광고의 공급률 검증은 아니었다.
- 위 변경은 아직 스토어 34에 반영되지 않았다. 후속 배포에서도 테스트 광고 성공만으로 운영 광고 미표시가 해결됐다고 보고하지 않는다.

기기 증거와 관리 화면 관측 요약은 `artifacts/ads-production-34-2026-10-31/`에 보관한다. 이번 조사에서는 제품 코드 변경, 빌드, 업로드와 스토어 제출을 하지 않았다.

## 후속 실기기 검증 35

사용자가 반복되는 단일 광고 노출을 보고하며 배포 전 실제 기기 재검사를 요청했다. 위의 34 로그 확인과 별개로, 이후 최신 소스를 운영 광고단위로 빌드해 추가 검증했다. 공개 배포는 재개하지 않았다.

### 설치와 승인 범위

- 기존 스토어 설치본의 Play 인증서 SHA-256은 `1eb08b0070eec45df48932aa43cdb28dcbca2f7c2278c29901120ca75db5dbb4`이며 로컬 업로드 키와 달랐다. 기존 앱을 삭제하지 않았다.
- 사용자가 35번 검증 파일의 출시 트랙 미지정 업로드와 미출시 파일 저장(commit)을 각각 허용했다. 전체 트랙이 업로드 전과 같은지 검사한 뒤 미지정 번들만 저장했다. 프로덕션, alpha, beta와 internal 트랙을 변경하지 않았고 TestFlight 제출도 하지 않았다.
- Google API가 `changesNotSentForReview=true` 옵션을 거부해 그 옵션을 제거했다. `ERROR_IF_IN_REVIEW`는 유지했다. 어떤 새 출시나 심사 대상 변경도 만들지 않았으며, 최종 트랙 확인에서 프로덕션은 34, alpha는 26, internal은 8로 유지됐다.
- Google이 서명한 일반 universal APK는 수동 설치 시 Play 다운로드 확인 화면으로 이동했다. 광고 실행에 도달하지 않은 이 결과는 광고 실패 통계에 섞지 않았다.
- 같은 번들에 대해 공식 Developer API가 제공한 개발자 검증용 APK 5개를 받았다. SDK 29 이상, arm64-v8a, xxhdpi와 한국어 및 영어 구성을 선택하고 각 서명이 기존 Play 인증서와 같은지 검증했다. 데이터 삭제 없이 `install-multiple -r`로 설치했다.
- 검증 앱은 운영과 같은 `com.minion.app`, 1.0.2(35), 운영 AdMob 앱 ID와 운영 배너 ID를 사용한다. 데모 ID와 테스트 기기 설정은 사용하지 않았다. 검증용 임시 Metro 계측과 SDK 실패 상세 로그만 추가했으며 제품 소스와 설치된 의존성 파일은 이 작업으로 바꾸지 않았다.
- 설치 경로는 ADB이고 개발자 검증 APK에는 Play의 자동 설치 경로 보호가 적용되지 않는다. 실제 스토어 다운로드 환경과 완전히 동일하다고 주장하지 않는다. 기기의 Play Protect나 계정 보안 설정은 변경하지 않았다.

### 실제 운영 광고 관측 결과: 미통과

Samsung SM-S906N에서 12:34:17~12:38:26 사이 한 번의 앱 실행을 유지하며 아래로 스크롤, 위로 복귀, 다시 아래로 스크롤했다. 광고를 클릭하지 않았고 앱 재시작이나 광고 ID 교체를 반복하지 않았다. 기존 지면별 지연 로딩, JS 재시도와 SDK 자체 갱신을 그대로 관측했다.

| 지면 | 첫 요청 준비 | 실패 콜백 | 성공 콜백 | 실제 노출 콜백 |
| --- | --- | ---: | ---: | ---: |
| home-top, 캘린더 아래 | 12:34:19 | 5 | 0 | 0 |
| home-teams, 팀 채널 뒤 | 12:34:53 | 2 | 2 | 2 |
| home-insights, 빌드 뒤 | 12:35:01 | 4 | 0 | 0 |

- 모든 실패의 네이티브 SDK 원문은 code 3, domain `com.google.android.gms.ads`, message `No fill.`, adapterCount 0, adapters `[]`였다. SDK가 광고 소스를 반환하지 않았다는 점까지 확인했으며, 빈 응답의 더 세부적인 서버 내부 사유는 제공되지 않았다.
- 초기에는 상단 지면만 요청됐고, 두 하단 지면은 스크롤 접근 후 요청됐다. 각 요청 너비는 379dp였다. 지면 누락이나 아직 요청하지 않은 placeholder를 공급 실패와 혼동하지 않았다.
- 팀 채널 뒤는 12:35:55와 12:37:56에 로드됐고, 12:36:33과 12:38:02에 실제 노출 콜백이 발생했다. 실물 광고 캡처에서도 해당 지면의 소재를 확인했다. 로드 크기는 약 378.67x58.67dp였다.
- JS가 호출한 재시도와 SDK 자체 갱신은 다르다. 이 기록에는 둘 다 포함되므로 전체 실패 수를 JS 재시도 최대 횟수와 같다고 해석하지 않는다.
- 운영 `https://minion.fan/app-ads.txt`는 HTTP 200이며 `google.com, pub-7060554754100656, DIRECT, f08c47fec0942fa0`으로 응답했다.

따라서 최신 코드에서도 세 지면의 실제 광고 노출 검사는 **미통과**다. 34에서 캘린더 아래만 보이던 상황과 달리 이번에는 팀 채널 뒤의 실제 노출을 확인했으나, 이를 세 지면 복구 완료로 해석하지 않는다. 레이아웃 변경이나 재배포만으로 광고 공급이 해결됐다고 보고하지 않는다. AdMob의 공급 상태에 대한 추가 원인 확인이 필요하다.

### 검증 후 상태

- 폰에는 데이터가 보존된 검증용 35가 남아 있다. 검증 종료 시 앱을 중지해 추가 자동 광고 요청을 멈췄다.
- USB 화면 유지 설정을 원래 값 0으로 복원했다.
- 스토어 프로덕션은 34 그대로다. 35는 트랙 미지정 진단 파일이고 **공개 배포용으로 사용하지 않는다**. 다음 정식 빌드에는 이미 등록된 35보다 큰 번호가 필요하다. EAS 원격 버전과 제품 app.json은 이번에 동기화하지 않았다.
- 서명, 패키지, 빌드 무결성 및 앱 타입 검사가 통과했고 성능 회귀 11개도 통과했다. 이는 실제 광고 노출 검사의 미통과를 대신하지 않는다.
- 재현 스크립트, 선택된 광고 로그, SDK 응답과 캡처는 `artifacts/ads-production-verify-2026-10-31/`에 보관한다. 업로드 키와 인증 토큰은 산출물에 포함하지 않는다.
